# 01. 実現可能性の検討（XIAO RP2040 でファミコン全マッパーを 1 チップ化できるか）

## 結論（先に）

| 項目 | 結論 |
|---|---|
| XIAO RP2040 **単体**でカートリッジバスを駆動 | **不可能**。使える GPIO は 11 本、必要なのは最低 27 本（バッファ IC で多重化した場合） |
| RP2040（Raspberry Pi Pico / 素の QFN-56） | **可能**。ただし SRAM 264KB の制約で、PRG+CHR ≤ 約 196KB のタイトル（ライセンス品の約 44%）に限られる |
| RP2350（Pico 2 / RP2350B） | **推奨**。SRAM 520KB で ≤ 約 440KB（ライセンス品の約 95%）、同じ配線・同じファームウェアで動く |
| マッパー自動判別 | iNES/NES 2.0 ヘッダ → CRC32 データベース（2,840 件）→ ヘッダ無しはサイズ推定、の 3 段構え（実装済み） |
| 拡張 IC の組み合わせ（例: MMC5 のバンク機能 + VRC7 音源） | **可能**。マッパー（バンク制御）と拡張音源（レジスタ窓）を分離し、プロファイルで自由に組み合わせる設計（ルーター実装済み、音源合成はフェーズ 2） |

## 1. ピン数

ファミコンのカートリッジ端子（60 ピン）でカートリッジ側が扱う必要のある信号:

| バス | 信号 | 本数 |
|---|---|---:|
| CPU | A0–A14, D0–D7, R/W, M2, /ROMSEL, /IRQ | 27 |
| PPU | A0–A13, D0–D7, /RD, /WR, CIRAM A10, CIRAM /CE | 26 |
| 音声 | 音声入力(45)→音声出力(46) | アナログ 2 |

合計 53 本のデジタル信号。XIAO RP2040 の GPIO は 11 本（GP0–4, GP6, GP7, GP26–29）。

### バッファ IC で多重化しても 27 本必要

アドレス 15 本を 8 ビット幅の 3 ステートバッファ 2 個で時分割読み出しし、データ 8 本をトランシーバ経由で同じ 8 本に重ねる「共有 8 ビットポート」方式でも:

- CPU 側ポート 8 + /ROMSEL 1 + セレクト 2 = 11
- PPU 側ポート 8 + /PPUACC（/RD と /WR の AND）1 + セレクト 2 = 11
- M2, /IRQ, CIRAM A10, CIRAM /CE = 4
- 音声 PWM = 1

= **27 本**。CPU バス（559ns 周期）と PPU バス（186ns 周期）は非同期に同時進行するため、両者を 1 つのポートに重ねることはできない。XIAO の 11 本では不足。

→ ピン数の多い RP2040 ボード（Pico 26 本 ※GP25 を音声 PWM に流用して 27 本確保 / 素の RP2040 30 本 / RP2350B 48 本）が必要。

## 2. タイミング

| 事象 | 数値 | 出典 |
|---|---|---|
| CPU クロック周期（M2） | 559 ns、High 350 ns（2A03E/G/H） | nesdev wiki "CPU pinout" |
| CPU 読み出しデータ確定期限 | M2 立ち下がり（+セットアップ ~100 ns） | 同上 |
| PPU メモリアクセス周期 | 186 ns（21.477 MHz / 4） | nesdev wiki "PPU pinout" |
| PPU /RD | 立ち下がりでアドレス確定、立ち上がりまでデータ保持 | nesdev wiki "Cartridge connector" |

RP2040 を 252 MHz（1 サイクル ≈ 4 ns）で動かした場合の見積り:

| 工程 | CPU バス | PPU バス |
|---|---:|---:|
| PIO でアドレス取り込み（バッファ切替 2 回） | ~50 ns | ~40 ns |
| コアへの通知（CPU: 割り込み / PPU: 専用コアのポーリング） | ~70 ns | ~10 ns |
| テーブル参照 `map[addr>>13][addr&0x1FFF]` と応答 | ~100 ns | ~60 ns |
| PIO が出力＋トランシーバ伝搬 | ~25 ns | ~25 ns |
| **合計** | **~245 ns**（期限 ≈ 350 ns − 100 ns = 250 ns） | **~135 ns**（期限 ≈ /RD Low 幅 ~300 ns 以上） |

CPU 側は余裕が薄い（約 ±50 ns）。対策として (a) 252〜266 MHz のオーバークロック、(b) CPU 側割り込みハンドラを SRAM 常駐（実装済み `FC_FASTCODE`）、(c) RP2350（Cortex-M33、150→300 MHz）への移行。

## 3. メモリ（なぜフラッシュから直接供給できないか）

RP2040 の XIP フラッシュはキャッシュミス時に QSPI 読み出し（コマンド+アドレス+ダミー+データ ≈ 30 クロック @126 MHz ≈ 240 ns 以上）が発生し、PPU の 186 ns 周期に間に合わない。したがって **PRG/CHR は起動時に SRAM へコピー**する。

| ボード | SRAM | ROM プール | 収まるタイトル（ライセンス品 2,233 本） |
|---|---:|---:|---:|
| RP2040 | 264 KB | 196 KB | PRG+CHR ≤ 192KB: 980 本 (43.9%) |
| RP2350 | 520 KB | 440 KB | ≤ 384KB: 2,092 本 (93.7%) / ≤ 512KB: 97.6%（PSRAM 併用で） |

ライセンス品のサイズ分布（Mesen DB 集計）: ≤64KB 20.8% / ≤128KB 38.5% / ≤256KB 86.6% / ≤512KB 97.6% / 最大 1MB（MMC3 TKROM 512K+256K など少数）。

## 4. 「1 チップ」の解釈

- **論理（マッパー・音源・判別）**: RP2040/RP2350 の 1 チップに集約（本ファームウェア）。
- **物理（5V バスとの接続）**: 3.3V ロジックへのレベル変換と 3 ステート化のため、74LVC 系バッファ 6 個 + デコーダ 1 個 + 単ゲート 1 個が必要。これはどの RP2040 系ボードでも避けられない（RP2350B で直結しても 5V トレラントではないため最低限のバッファは要る）。

## 5. XIAO RP2040 の位置づけ（本プロジェクトでの扱い）

- `FC_BOARD=xiao_rp2040` でビルドすると、バス処理を除いた同一ファームウェア（ROM 判別・マッパー自己診断・拡張音源合成・USB CDC ログ）が動く。音源ミキサーや ROM スロット形式のベンチ確認に使える。
- 実機カートリッジとして動かすには Pico / Pico 2 / 自作 RP2350B 基板を使う（配線は `docs/04_hardware.md`）。
