## この表の読み方

- 単位は DB の行（ダンプ・版ごとに 1 行）で、タイトルの数ではない。NES（NTSC・PAL）の行と、基板名のある非ライセンス基板（COLORDREAMS、AVE、TENGEN、CAMERICA など）も含む。
- 「実装」は、そのマッパー番号がファームに登録されているという意味。基板の全機能が動くことまでは示さない（下の表）。
- ファミコンの行（基板名あり）は **940 行**で、未登録のマッパーを使う行は **0 行**。基板名のないファミコンの行（629 行、海賊版・マルチカートの番号が中心）は集計に入れていない。

## RAMBO-1（マッパー 64・158）の確認とシリコン解析の取り込み（2026-11-15〜16）

資料:
- furrtek 氏の SiliconRE「Misc/RAMBO-1」（https://github.com/furrtek/SiliconRE/tree/master/Misc/RAMBO-1 。README.md、ゲート回路図 RAMBO-1_schematics.pdf〔5 ページ〕、ダイのトレース RAMBO-1_trace.svg／.png。GPL-2.0）。回路の動きを参照しただけで、ファイルはこのリポジトリに入れていない。リポジトリの README の「License」の節には、作者がこの情報をモデルの学習や AI によるコード・データの生成に使うことに反対していると書かれている。依頼者はこれを知らされたうえで、回路図から読み取れた点も取り込むと決めた（2026-11-15）。
- nesdev wiki の RAMBO-1 と INES Mapper 158（https://www.nesdev.org/wiki/RAMBO-1 、https://www.nesdev.org/wiki/INES_Mapper_158 。2026-11-15 時点）。
- James 氏が 2013 年に実機のカセットで測った IRQ の時刻（https://forums.nesdev.org/viewtopic.php?t=10439 ）。スキャンライン方式の /IRQ は、PPU A12 の立ち上がりから CPU 1.04〜1.95 サイクル後に下がる。
- 依頼者から示されたフォーラムのスレッド（[t=1219 の 10 ページ目](https://forums.nesdev.org/viewtopic.php?t=1219&start=135)）は CIC（ロックアウトチップ）の解析の話で、マッパーとしての RAMBO-1 の記述はなかった。ファミコン（60 ピン）は CIC を使わない。

下の「pN」は回路図のページ、英数字はセル名。

確認できたこと（コードはそのまま）:
- レジスタは CPU A14・A13・A0 だけで選ばれ、$8000〜$FFFF の中で繰り返す（p1 D19）。$A001 はどこにもつながっておらず、番号 $A〜$E のレジスタはない（p1 D12）。$8000 の bit 4 は記憶されるが使われない。
- CHR の割り当て（K=0 では R0・R1 が 2 KB で CHR A10 = PPU A10、K=1 では R0・R8・R1・R9、R2〜R5 は常に 1 KB、C で前後の半分を入れ替える。p5 G20・G9・G14）。PPU A13 を見ないので、ネームテーブルの読み出し中も CHR のバンク線は出ている。158 はこの CHR A17 を CIRAM A10 に使う。wiki の記述とも一致。
- $E000〜$FFFF は常に最後のバンク（p5: CPU A13 = 1 では OR A38・E32・A26・A25・E37・A40 が CPU A14 で全ビットを 1 にする）。$A000 の bit 0 が CIRAM A10 の選択（0 = PPU A10 で垂直、1 = PPU A11 で水平。p1 F22・G41）。bit 1 は未ボンディングのパッドにしかつながらない。
- バンク関係のセルにはリセットがなく、電源投入時の値はすべて不定。ファームの初期値は変えていない。

直したこと（`src/core/mappers/m064_rambo1.c`、`src/core/mapper_state.h`。テストは `test/tm_unl.c` の `t_64` と `t_158`）:
- **PRG**: $8000 の bit 6（P）は $8000 と $C000 を入れ替えるだけ。P=1 では $8000 = RF、$A000 = R7、$C000 = R6（wiki の表どおり。p5: F23 = P xor CPU A14 が MUX21 B28・D16・C27・B26・C28B・B31 で R6 と RF を選ぶのは CPU A13 = 0 のときだけで、CPU A13 = 1 は R7 OR CPU A14）。以前は $A000 = R6、$C000 = R7 と回していた。
- **A12 のフィルタ**: M2 で動く 16 段のフリップフロップの列（p3 J38 から J41 まで。各段は前の段でリセットされる）なので、A12 が M2 16 回分 Low だった後の立ち上がりだけを数える。以前は PPU の読み出し 3 回分で、BG を $1000 に置くと行の境目のネームテーブル読み出しでも数え、1 行に 2 回進んでいた（ホストでの再現で確認）。
- **カウンタのクロック**: カウンタは H37 のマルチプレクサの出力が立ち上がるたびに動く。CPU 方式ではその出力は /4 分周器（G52）、スキャンライン方式では H41 の /Q（フィルタが満ちていない間 High）で、A12 が再び High になってから最初の M2 の立ち上がりで立ち上がる。
- **$C001**: カウンタを $FF にし（p3 M47 → CLR）、/4 分周器を 0 に戻し（H40・G52）、R2 を立てて R4 を下ろす。R4 はマルチプレクサの出力が下がるときに R2 を取り込み、その次のクロックでラッチを書いた値のまま読み込む（「| 1」はない）。このため、書き込みが終わったときに出力が High なら 1 回目のクロックで、Low なら 2 回目のクロックで読み込む（1 回目は $FF → $FE の減算）。
  - CPU 方式のまま書くと出力は Low。2 サイクル目に $FF → $FE、6 サイクル目にラッチを読み込み、以後 4 サイクルごとに減る。/IRQ は書き込みから 4L+7 サイクル目に見え、以後 4(L+1) サイクルごと。書き込みのときの分周器の位相にはよらない。
  - スキャンライン方式では、A12 が High か、Low になってから M2 16 回未満のときに書くと L+1 回目、M2 16 回以上 Low が続いてフィルタが満ちているときに書くと L+2 回目の立ち上がりで IRQ。wiki の「Klax には +1 が要る」は、後者の $FF → $FE の 1 回と合う（Klax がどの状態で書いているかは未確認）。
  - 方式の切り替えでは、マルチプレクサの入力の切り替えそのものが出力の端になる。スキャンライン方式で出力が High のときに CPU 方式へ切り替えると立ち下がりになり、1 回目のクロックで読み込む（/IRQ は 4L+3 サイクル目）。逆向きの立ち上がりは CLR の間のクロックで、見える変化はない。
  - 書き込みの直前のクロックで 0 になった分の IRQ は出ない（G49 が取り込むときにはカウンタは $FF に戻っている）。すでに出ている IRQ はそのまま（G50 は戻らない）。
- **IRQ を出す条件**: 0 でない値から 0 になったクロックだけ（G49 が M2 の立ち下がりごとに「0 か」を取り込み、G50 がその立ち上がりで立つ）。ラッチが 0 なら 1 回だけ（以前は毎クロック）。$FF や $FE から 0 を読み込んだときも 1 回と数える。
- **/IRQ の遅れ**: カウンタと出力の間にあるのは G49 だけで、0 になったクロックの後の最初の M2 の立ち下がりで /IRQ が下がる。スキャンライン方式では A12 の立ち上がりから 2 回目の M2 の立ち下がり（CPU 1〜2 サイクル後で、James 氏の実測 1.04〜1.95 サイクルと合う。wiki の「M2 が 2 回下がるまで遅れる」とも合う）。以前はどちらの方式も 3 サイクル後だった。
- **$E000・$E001**: $E000 は G50 をリセットしたままにする（E38）ので、まだ出ていない IRQ も消える。$E001 は許可するだけで、$E001 と $C001 は出ている IRQ を取り下げない。
- **状態の構造体**: `prg_mode` を分周器に流用していたのと、2026-11-15 の途中版で足した `irq_delay` をやめ、`irq_next`（次のクロックまでの M2 の数）、`irq_due`、`a12_hi`、`a12_low_since` を足した。この構造体の並びに依存するコードはない。

照合の方法: 回路図 p3 から別の担当者が起こしたゲートモデル（C。作業用で、リポジトリには入れていない）と famicart の実コードに同じ書き込みと A12 の列を与え、/IRQ を毎サイクル比べた。結果はすべて 0 サイクルの不一致。
- CPU 方式、$C000・$C001・$E000・$E001 を乱数で書く: 20 回 × 20,000 サイクル。
- スキャンライン方式、NTSC の PPU の読み出しの列を再現: BG $0000 とスプライト $1000、BG $1000 とスプライト $0000、8×16 スプライトで両方の表を使い BG $0000 か $1000 の 4 通り × L = 0・1・2・3・7・20 × $C001 を垂直帰線期間に書くか 100 行目の 300 ドット目に書くか、各 3 フレーム。
- 両方式を混ぜる: $C001 の方式も乱数にし、どのサイクルにも書き込みを入れ、A12 の High・Low の長さを 1〜140 M2（16 M2 の前後を多めに）にして、200 回 × 50,000 サイクル（IRQ 18,856 回）。

回路図だけでは決まらなかったことと、その決め方: カウンタのセル（CNTCELL）がクロックのどちらの端で動くかは、図からは決まらない。記号どおり（R6 の出力の立ち上がり = マルチプレクサの出力の立ち下がり）に読むと、スキャンライン方式のカウンタは A12 の立ち上がりではなくフィルタが満ちたとき（BG $0000 なら次の行の約 30 ドット目）に進み、/IRQ は A12 の立ち上がりから大きく遅れる。これは James 氏の実測と合わないので、マルチプレクサの出力の立ち上がりで動くとして両方式を組んだ（記号どおりの読み方のゲートモデルとは、CPU 方式で 20 回 × 20,000 サイクルのうち 3,674 サイクル食い違う）。

残っている問題:
- CPU 方式の時刻は、ゲートモデルとは一致するが、実機での測定値とは照らし合わせていない。実機のカセットで M2・PPU A12・/IRQ をロジックアナライザで測れば確かめられる。Skull & Crossbones の表示の乱れとの関係も未確認。
- PRG のレジスタは 6 ビット（D5 は未ボンディングの PRG A18）だが、ファームは 8 ビットのまま（256 KB 以下の ROM では違いが出ない）。
- 158 の CIRAM A10 の配線は基板の話で、チップからは確かめられない。$3000〜$3EFF の読み出しでは CHR の反対側の半分が出るはずだが未実装（使うゲームは知られていない）。
- rev D では U2 が M2 を見ないので、スキャンライン方式の IRQ が出ない（変更前から。U2 の PPU フックだけではフィルタもクロックも進まない）。
